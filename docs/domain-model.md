# Предметная область EFITA MOON

## 1. Назначение документа

Этот документ фиксирует первоначальную модель данных для MVP сайта EFITA MOON.

EFITA MOON — сайт-каталог авторских украшений ручной работы. В первой версии посетитель сможет просматривать категории и украшения, а также оставлять контактные данные для связи по поводу конкретного изделия.

На этапе MVP сайт не содержит:

- корзины;
- онлайн-оплаты;
- автоматического оформления заказа;
- расчета доставки;
- личного кабинета покупателя.

Заявка посетителя не является полноценным заказом. Она означает, что человек заинтересовался конкретным украшением и хочет, чтобы с ним связались.

## 2. Основные сущности

Для первой версии предусмотрены следующие сущности:

- Category — категория украшений;
- Product — украшение;
- OrderRequest — заявка посетителя на связь по поводу украшения;
- Admin — администратор сайта.

На первом этапе разработки планируется сначала реализовать Category и Product.

OrderRequest будет реализована отдельным следующим этапом после появления работающего каталога.

Admin будет реализован позднее вместе с административной частью сайта.

## 3. Связи между сущностями

```text
Category
  has_many :products

Product
  belongs_to :category
  has_many :order_requests

OrderRequest
  belongs_to :product
```

Одна категория может содержать много украшений.

Каждое украшение относится к одной категории.

По одному украшению может быть оставлено несколько заявок от разных посетителей.

Удаление связанных данных должно быть отдельно согласовано перед реализацией. На этапе проектирования не фиксируется автоматическое каскадное удаление товаров и заявок.

## 4. Category

### Назначение

Category объединяет украшения по месту ношения и используется для построения каталога.

Текущие публичные категории:

- На шею — Чокеры · Колье · Сотуары;
- На уши — Серьги;
- На руки — Браслеты;
- На ноги — Анклеты;
- На сумку — Обвесы · Подвески.

Категории должны храниться в базе данных, а не быть зашитыми в код. Это позволит администратору в дальнейшем добавлять и изменять категории без изменения приложения.

### Поля Category

| Поле         | Тип      |  Обязательное | Назначение                              |
| ------------ | -------- | ------------: | --------------------------------------- |
| `name`       | string   |            да | Название категории, например «На шею»   |
| `slug`       | string   |            да | Человекочитаемая часть URL              |
| `subtitle`   | string   |           нет | Подпись категории, например виды внутри |
| `position`   | integer  |            да | Порядок категории в каталоге            |
| `active`     | boolean  |            да | Показывается ли категория посетителям   |
| `created_at` | datetime | автоматически | Дата создания                           |
| `updated_at` | datetime | автоматически | Дата последнего изменения               |

### Правила Category

#### `name`

- не может быть пустым;
- должно быть уникальным;
- хранится на русском языке;
- пример: `На шею`.

#### `subtitle`

Используется как редактируемая подпись категории в публичном каталоге и админке.

Примеры:

```text
Чокеры · Колье · Сотуары
Обвесы · Подвески
```

Правила:

- может быть пустым;
- если значение пустое, публичные шаблоны не выводят отдельный пустой HTML-элемент.

#### `slug`

Используется в адресе страницы категории.

Примеры:

```text
/catalog/neck
/catalog/ears
/catalog/hands
```

Правила:

- не может быть пустым;
- должно быть уникальным;
- хранится латиницей;
- используется в нижнем регистре;
- слова разделяются дефисами;
- не должно изменяться без необходимости после публикации категории.

На первом этапе slug можно вводить вручную через административную часть. Автоматическую генерацию slug следует рассмотреть позднее.

#### `position`

Определяет порядок отображения категорий.

Например:

```text
0 — На шею
1 — На уши
2 — На руки
3 — На ноги
4 — На сумку
```

Значение должно быть целым неотрицательным числом.

#### `active`

Возможные значения:

- `true` — категория показывается в публичной части;
- `false` — категория скрыта.

Значение по умолчанию:

```text
true
```

Скрытие категории не должно автоматически удалять товары из базы данных.

## 5. Product

### Назначение

Product представляет конкретное украшение EFITA MOON.

Каждое украшение относится к одной категории и отображается в публичном каталоге только при выполнении условий публикации.

### Поля Product

| Поле          | Тип                     |  Обязательное | Назначение                         |
| ------------- | ----------------------- | ------------: | ---------------------------------- |
| `category_id` | foreign key             |            да | Категория украшения                |
| `title`       | string                  |            да | Название украшения                 |
| `slug`        | string                  |            да | Человекочитаемая часть URL         |
| `description` | text                    |            да | Описание украшения                 |
| `size`        | string                  |           нет | Размер или длина изделия           |
| `materials`   | text                    |           нет | Материалы изделия                  |
| `price`       | decimal                 |            да | Цена                               |
| `status`      | string или integer enum |            да | Статус наличия                     |
| `published`   | boolean                 |            да | Показывать ли украшение в каталоге |
| `created_at`  | datetime                | автоматически | Дата создания                      |
| `updated_at`  | datetime                | автоматически | Дата последнего изменения          |

Артикул в первой версии не используется.

Для внутренней идентификации достаточно стандартного `id`, а для публичных адресов используется `slug`.

### Правила Product

#### `category_id`

- обязательно;
- должно ссылаться на существующую Category;
- одно украшение относится только к одной категории.

#### `title`

- не может быть пустым;
- является пользовательским названием изделия;
- не обязано быть уникальным.

Примеры:

```text
Лунный свет
Сердце льва
Тихий блеск
```

Для Category используется поле `name`, а для Product — `title`. Это разделение делает код понятнее:

```ruby
category.name
product.title
```

#### `slug`

Используется в публичном URL украшения.

Примеры:

```text
/products/moonlight-choker
/products/lion-heart-necklace
```

Правила:

- не может быть пустым;
- должно быть уникальным;
- хранится латиницей;
- используется в нижнем регистре;
- слова разделяются дефисами.

На первом этапе slug можно вводить вручную. Автоматическую генерацию следует рассмотреть позднее.

#### `description`

Содержит описание украшения, его настроения, особенностей и деталей.

Правила:

- не может быть пустым;
- хранится как многострочный текст;
- не должно содержать HTML, введенный пользователем, без отдельной обработки и очистки.

#### `size`

Хранится строкой, поскольку у разных украшений используются разные способы описания размера.

Примеры:

```text
36 см + удлинитель 5 см
17 см
45 см
Диаметр камня 8 мм
```

Строковый формат выбран сознательно, чтобы не создавать преждевременно отдельные поля для числа, единицы измерения и типа размера.

В будущем при необходимости модель можно расширить структурированными характеристиками.

#### `materials`

Хранится как текст, потому что одно украшение обычно содержит несколько материалов.

Примеры:

```text
Гематит, горный хрусталь, ювелирный сплав
Натуральный жемчуг, стекло, сталь
```

В первой версии материалы не являются отдельной сущностью и не используются для фильтрации.

#### `price`

Для хранения цены должен использоваться тип `decimal`, а не `float`.

Планируемые параметры:

```ruby
precision: 10
scale: 2
```

Пример:

```text
2500.00
```

Правила:

- не может быть пустой;
- должна быть больше или равна нулю;
- валюта на первом этапе не хранится в каждой записи;
- приложение предполагает единую основную валюту.

Основная валюта — рубли, формат отображения: `2 500 ₽`.

- основная валюта MVP — российский рубль;
- валюта не хранится отдельно в каждой записи Product;
- в базе цена хранится как decimal с precision: 10, scale: 2;
- в публичном интерфейсе цена отображается в формате 2 500 ₽;
- форматирование цены относится к представлению, а не к модели;
- если в будущем появится поддержка нескольких валют, модель данных будет пересмотрена.

#### `status`

Статус отражает возможность приобрести украшение.

Для MVP используются три состояния:

```text
available
made_to_order
unavailable
```

Значения:

- `available` — товар готов и находится в наличии;
- `made_to_order` — готового изделия нет, но его можно изготовить или повторить под заказ;
- `unavailable` — товар сейчас нельзя купить или заказать.

Отображение в интерфейсе:

```text
available     → В наличии
made_to_order → Доступен к заказу
unavailable   → Нет в наличии
```

Статус по умолчанию:

```text
available
```

Статус не определяет видимость украшения на сайте. За видимость отвечает отдельное поле `published`.

`status` отвечает за возможность приобретения, а `published` отвечает за публичную видимость.

Опубликованный товар может иметь любой из трех статусов: `available`, `made_to_order` или `unavailable`.

`made_to_order` не является категорией каталога. Категории по-прежнему описывают тип изделия.

#### `published`

Определяет, показывается ли украшение посетителям.

Возможные значения:

- `true` — украшение опубликовано;
- `false` — украшение является черновиком или временно скрыто.

Значение по умолчанию:

```text
false
```

Новый товар сначала создается как черновик. После заполнения данных и добавления фотографий администратор сможет опубликовать его.

Публичный каталог должен показывать только товары, у которых:

```text
published = true
```

При этом товар с любым статусом, включая `made_to_order` или `unavailable`, может оставаться опубликованным, если его нужно показывать посетителям.

## 6. Фотографии Product

Фотографии не хранятся отдельной моделью ProductImage на первом этапе.

Планируется использовать Active Storage:

```ruby
has_many_attached :images
```

Одно украшение сможет иметь несколько фотографий.

Правила работы с фотографиями, порядок изображений, главное изображение, ограничения по формату и размеру будут описаны отдельно перед подключением Active Storage.

## 7. OrderRequest

### Назначение

OrderRequest — заявка посетителя на связь по поводу конкретного украшения.

Это не полноценный заказ и не подтверждение покупки.

Сценарий MVP:

```text
Посетитель открывает страницу украшения
→ нажимает кнопку «Оставить заявку»
→ указывает имя и контакт
→ при необходимости пишет комментарий
→ заявка сохраняется
→ администратор связывается с посетителем вручную
```

OrderRequest будет реализована после работающего каталога и страниц украшений.

### Планируемые поля OrderRequest

| Поле         | Тип                     |  Обязательное | Назначение                              |
| ------------ | ----------------------- | ------------: | --------------------------------------- |
| `product_id` | foreign key             |            да | Украшение, по которому оставлена заявка |
| `name`       | string                  |            да | Имя посетителя                          |
| `contact`    | string                  |            да | Телефон, Telegram или email             |
| `message`    | text                    |           нет | Комментарий посетителя                  |
| `status`     | string или integer enum |            да | Статус обработки заявки                 |
| `created_at` | datetime                | автоматически | Дата создания                           |
| `updated_at` | datetime                | автоматически | Дата последнего изменения               |

### Планируемые статусы OrderRequest

```text
new_request
contacted
closed
```

Отображение в интерфейсе:

```text
new_request → Новая
contacted   → Связались
closed      → Закрыта
```

Статус по умолчанию:

```text
new_request
```

Перед реализацией OrderRequest набор полей и статусов должен быть повторно проверен на соответствие реальному процессу обработки заявок.

## 8. Admin

Admin будет представлять пользователя, имеющего доступ к закрытой административной части сайта.

Планируется авторизация через:

```ruby
has_secure_password
```

и гем:

```ruby
bcrypt
```

Минимально предполагаются поля:

| Поле              | Тип      |  Обязательное | Назначение                |
| ----------------- | -------- | ------------: | ------------------------- |
| `email`           | string   |            да | Логин администратора      |
| `password_digest` | string   |            да | Безопасный хеш пароля     |
| `created_at`      | datetime | автоматически | Дата создания             |
| `updated_at`      | datetime | автоматически | Дата последнего изменения |

Пароль в открытом виде в базе данных храниться не должен.

Проектирование сессий, восстановления доступа и ограничений административных маршрутов будет выполнено отдельным этапом.

## 9. Решения, отложенные на будущее

В MVP не добавляются без реальной необходимости:

- артикул или `product_code`;
- корзина;
- полноценная сущность Order;
- позиции заказа;
- количество товара;
- онлайн-оплата;
- доставка;
- адрес клиента;
- личный кабинет;
- избранное;
- отзывы;
- материалы как отдельная сущность;
- размеры как отдельная сущность;
- складской учет;
- остатки товара;
- несколько валют;
- скидки и промокоды;
- автоматические уведомления;
- SEO-метаданные для каждой страницы;
- автоматическая генерация slug;
- удаление изображений по сложным правилам.

Каждое из этих решений может быть добавлено отдельной миграцией и отдельной функцией после появления реальной потребности.

## 10. Порядок реализации

Предварительный порядок:

1. Зафиксировать модель данных в документации.
2. Реализовать Category.
3. Реализовать Product.
4. Добавить тесты моделей.
5. Создать публичный каталог на реальных данных.
6. Создать страницу отдельного украшения.
7. Подключить Active Storage и изображения.
8. Реализовать OrderRequest.
9. Реализовать Admin и авторизацию.
10. Создать административную часть.
